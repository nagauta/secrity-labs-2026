# secrity-labs-2026 — セキュリティ学習ラボ

IPA「[安全なウェブサイトの作り方](https://www.ipa.go.jp/security/vuln/websecurity/about.html)」で
解説される主要な脆弱性を、**インターネットから隔離された Docker 環境**で再現する教材です。
攻撃の仕組みを手を動かして理解し、同時に「どう直すか」も学びます。

実装言語は **TypeScript**（target は Hono、attacker は Node 標準モジュール、どちらも `tsx` で実行）。

## ⚠️ 安全のための大前提

- **ローカル隔離**: 公開ポートは `127.0.0.1` のみにバインド。外部ネットワークへは出しません。
- **教育目的のみ**: 意図的に脆弱なアプリです。本番・公開サーバには絶対に置かないこと。
- **自分の環境だけが対象**: ラボ内の自分のコンテナ以外を攻撃する用途には使いません。
- DVWA / OWASP WebGoat / Juice Shop と同じカテゴリの、定番の学習用やられアプリです。

## 構成

| コンテナ | 役割 | 公開先 |
|----------|------|--------|
| `target`   | Hono 製のやられ役SNS「つなぐ」（`/sns/widget` に埋め込み「いいね」ボタン） | `127.0.0.1:8080` |
| `attacker` | ラボのシェル（`index.html`）と各攻撃デモを配信する静的サーバ | `127.0.0.1:9090` |

両コンテナは Docker ネットワーク `labnet` に属します。

## 使い方（ラボのトップ）

`http://localhost:9090/` を開くと、**左サイドバーから攻撃の種類を選べるラボ画面**が出ます。
実装済みのモジュールを選ぶと、右側にデモが開きます。未実装のものは「準備中」と表示されます。
各攻撃デモ（例: `evil-sns.html`）は単体URLでも直接開けます。

## モジュール1: クリックジャッキング（ライクジャッキング）

2010年に Facebook で流行した「いいね！」ボタン乗っ取り（ライクジャッキング）の
再現です。標的の「いいね」ボタンを透明で重ね、別の操作を押させることで、
ログイン中の本人として勝手に「いいね」させ、拡散投稿を本人のタイムラインに流します。

### 起動

```bash
docker compose up --build
```

### 攻撃を体験する

1. ブラウザで `http://localhost:9090/` を開き、左サイドバーの「クリックジャッキング」を選ぶ
   → 「衝撃映像」を餌にしたおとりページが開く（起動時の既定でも選択済み）。
2. 「▶ 再生する」を押す。
3. 実際には裏に透明で重なった SNS『つなぐ』の「👍 いいね！」が押され、拡散投稿
   （例: `【拡散中】絶対見て！衝撃映像 bit.ly/xxxx`）に本人としていいねしてしまう。
4. いいねを盗んだ直後、攻撃者ページはオーバーレイを外して**本物のネコ動画を再生**する。
   利用者は「普通に再生できた」と思い、乗っ取りに気づかない。
5. `http://localhost:8080/sns` を直接開くと、押した覚えのない投稿が自分のタイムラインに
   いいね済みで並んでいることを確認できる（＝友達のフィードにも流れて拡散する）。

> 💡 右上の学習用コントロールで、仕掛けと対策を観察できます。
> - **「オーバーレイ(いいねボタン)を表示」**: 再生ボタンの上に透明で重ねた
>   「いいね」ボタンと、**攻撃者の狙い（シナリオ解説）**が表示されます。
> - **「🛡 対策を有効化（フレーム化を拒否）」**: 標的が `X-Frame-Options: DENY` を
>   返した状態を再現します。いいねボタンが埋め込めず（「フレーム表示を拒否」の表示）、
>   再生を押しても**いいねは盗まれません**（＝攻撃失敗）。状態バッジが「脆弱／対策済み」で
>   切り替わります。

### なぜ成立するのか（脆弱点）

埋め込み用ウィジェット `/sns/widget` が、フレーム化を禁止するレスポンスヘッダ
（`X-Frame-Options` も `Content-Security-Policy: frame-ancestors`）を
**一切返していない**ため、任意の外部サイトから `<iframe>` で重ねられてしまいます。
該当箇所は `target/server.ts` の `/sns/widget` ハンドラとその上のコメントを参照。

### 対策

`target/server.ts` 冒頭にコメントアウトされている `app.use(...)` を有効化すると、
以下のどちらか（両方でも可）が全レスポンスに付与され、攻撃が成立しなくなります。

- `X-Frame-Options: DENY` — iframe 埋め込みを全面拒否（古くからある専用ヘッダ）
- `Content-Security-Policy: frame-ancestors 'none'` — 祖先フレームを一切許可しない（現代的な方法）

有効化して `docker compose up --build` で再起動し、同じ手順で攻撃が
**失敗する**（iframe がブロックされ、再生ボタンを押しても何も起きない）ことを確認してください。

> 補足: 本物の Facebook は攻撃者サイトと別ドメイン（cross-site）のため、現代ブラウザの
> サードパーティ Cookie ブロックや SameSite Cookie も防御として働きます。本ラボは
> `localhost` 同士（same-site）なので、その影響を受けずに仕組みを観察できるよう、
> セッションではなく単純なサーバ状態で「ログイン中の本人」を再現しています。

### 学習後のリセット

```bash
curl -X POST http://localhost:8080/sns/reset
```

## モジュール2: XSS（クロスサイトスクリプティング）

実在事例「**2005年 MySpace の Samy ワーム**」（Samy Kamkar）の再現です。プロフィールの
自由記述に JavaScript を仕込める蓄積型XSSを悪用し、「samy is my hero」を他人のプロフィールへ
勝手に追記しつつ、そのスクリプト自体を閲覧者へ複製して約20時間で100万人超へ自己増殖しました。

架空SNS『つなぐ』では、攻撃者サミー(@samy)の「ひとこと」に仕込んだ `<script>` が、
閲覧者のブラウザで動いて本人として拡散投稿に「いいね」し、同じスクリプトを閲覧者自身の
「ひとこと」へ複製して自己増殖します（蓄積型）。あわせて検索語をそのまま反射する反射型XSSも実演します。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「XSS」を選ぶ → おとりの「プロフィール診断メーカー」が開く。
2. 埋め込まれた攻撃者サミーのプロフィールが表示され、`<img onerror=...>` が実行される。
3. `http://localhost:8080/sns` を開くと、押した覚えのない「いいね」が増えている。
4. 反射型のリンク（`/sns/search?q=<script>...`）を踏むと、その場で script が動く。

### なぜ成立するのか（脆弱点）

- 蓄積型: `target/app.ts` の `/sns/users/:name` が `profile.bio` を**無エスケープ**で HTML に埋め込む。
- 反射型: `/sns/search` が `?q` をそのまま結果ページへ**無エスケープ**で反射する。

### 対策

出力時に `<` `>` `"` `'` `&` を HTML エンティティへ**エスケープ**すれば、入力はただの文字列として
表示され script は実行されません（`app.ts` の `escapeHtml()` コメントを参照）。あわせて
`Content-Security-Policy: script-src 'self'` でインラインスクリプトを禁止すると多層防御になります。

## モジュール3: SQLインジェクション

実在事例「**2011年 Sony Pictures の情報漏えい**」（LulzSec）の再現です。SQLインジェクションで
会員DBが抜かれ、約100万件のアカウントが流出。しかもパスワードが平文保存で、そのまま使える
状態だったと報じられました。古典の `' OR '1'='1` ログインバイパスも同じ原理です。

架空SNS『つなぐ』では、会員ログインと会員検索が入力値を SQL にそのまま文字列連結しています。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「SQLインジェクション」を選ぶ → 偽のログインページが開く。
2. **認証バイパス**: ユーザー名に `admin'--` を入れて送信 → パスワード不要で `admin` としてログイン
   （`{ok:true, loggedInAs:"admin"}`）。
3. **UNION 窃取**: 会員検索リンク（`' UNION SELECT ... --`）を踏むと、本来見えない平文パスワードや
   秘密メモ（例: 管理者用バックアップ鍵）まで JSON で漏れる。

### なぜ成立するのか（脆弱点）

`target/app.ts` の `/sns/login` と `/sns/members` が、入力を
`... WHERE username = '${input}'` のように**文字列連結**している（プレースホルダ未使用）。

### 対策

`db.prepare('... WHERE username = ? AND password = ?').get(u, p)` のように**プレースホルダ
（パラメータバインド）**で値を渡せば、入力は必ず「データ」として扱われ、`admin'--` や
`UNION` は SQL として解釈されません（`app.ts` のコメント参照）。

## モジュール4: OSコマンドインジェクション

実在事例「**2014年 Shellshock**（CVE-2014-6271）」の再現です。bash の環境変数処理の欠陥を突いて
CGI 経由などで Web サーバ上に任意の OS コマンドを実行され、多数のサーバが乗っ取られました。
「Web からの入力が最終的にシェルに渡る」典型例で、管理画面の ping/traceroute 診断機能に
`;` や `&&` を混ぜる古典的な注入も同じ原理です。

架空SNS『つなぐ』では、運営の管理画面に「サーバ疎通確認（ping）」ツールがあり、入力ホスト名を
そのまま `ping -c 1 <host>` に連結してシェル実行しています。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「OSコマンドインジェクション」を選ぶ → 運営ツール風のページが開く。
2. 対象ホスト欄に `127.0.0.1; cat /etc/passwd` を入れて「実行」 → ping のあとに `cat` が走り、
   `/etc/passwd` の中身が応答に漏れる。
3. `; `、`&&`、`` `...` ``、`$(...)` などで任意コマンドを継ぎ足せることを確認する。

### なぜ成立するのか（脆弱点）

`target/app.ts` の `/admin/net/ping` が、入力を `ping -c 1 ${host}` という**コマンド文字列に
連結**し、`exec`（シェル経由）で実行しているため、`;` や `&&` がメタ文字として効いてしまう。

### 対策

`execFile('ping', ['-c','1', host])` のように**シェルを介さず引数配列**で渡せば、メタ文字は
ただの文字列になります。あわせて `/^[A-Za-z0-9.-]+$/` などで**入力を検証**するのが根本対策です
（`app.ts` のコメント参照）。

## モジュール5: パストラバーサル（ディレクトリトラバーサル）

実在事例「**2021年 CVE-2021-41773**（Apache HTTP Server 2.4.49）」の再現です。URL の正規化
不備で `..%2f` を使ったパストラバーサルが可能になり、ドキュメントルート外のファイル閲覧や
（条件次第で）リモートコード実行まで引き起こしました。古典の `../../etc/passwd` と同原理です。

架空SNS『つなぐ』では、投稿の「添付ファイル」を名前で取り出す機能が、公開ディレクトリ
（`uploads`）に対して入力ファイル名を結合するだけで中身を返します。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「パストラバーサル」を選ぶ → 添付ファイルビューアが開く。
2. `welcome.txt` は正常に表示される。
3. ファイル名に `../../../../../../etc/passwd` を入れて「開く」 → 公開ディレクトリ外の
   `/etc/passwd` が読める。`../package.json` でアプリ自身のソース情報も漏れる。

### なぜ成立するのか（脆弱点）

`target/app.ts` の `/sns/files` が、入力ファイル名を検証せず `join(UPLOAD_DIR, name)` して
読み出すため、`../` を重ねると公開範囲の外へ出られる。

### 対策

`resolve(UPLOAD_DIR, name)` で正規化した結果が**公開ディレクトリ内に収まっているか**を
`relative()` で検証し、外に出る場合は拒否します。あわせて入力から `..` やパス区切りを
弾くと多層防御になります（`app.ts` のコメント参照）。

## モジュール6: CSRF（クロスサイトリクエストフォージェリ）

実在事例「**2006年 Netflix の CSRF**」の再現です。ログイン中の利用者が攻撃者ページを開くだけで、
本人の意思と無関係に「配送先住所の変更」「レンタル希望リストへの追加」などが勝手に実行されました。
状態を変える操作に CSRF 対策（トークン等）が無いために成立します。

架空SNS『つなぐ』では、アカウントのメールアドレス変更が、ログイン状態だけを頼りに POST を
受け付けます（CSRFトークンも Origin 検査も無し）。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「CSRF」を選ぶ → 偽の「プレゼント当選」ページが開く。
2. ページを開いた瞬間、裏で `POST /account/email` が自動送信され、登録メールが
   `attacker@evil.example` に書き換わる（利用者は気づかない）。
3. メールを奪えれば、攻撃者はパスワード再設定からアカウントを乗っ取れる。

### なぜ成立するのか（脆弱点）

`target/app.ts` の `/account/email` が、状態変更 POST に **CSRFトークンも Origin/Referer 検査も
SameSite Cookie も無い**まま、ログイン状態だけで受け付けている。

### 対策

フォーム表示時に発行した**CSRFトークン**を必須にし、送信値と一致しなければ拒否します
（攻撃者は正しいトークンを知り得ない）。あわせて **Origin/Referer の検査**や
`Cookie; SameSite=Lax` も有効です（`app.ts` のコメント参照）。

> 補足: 本ラボは `localhost` 同士（same-site）で、セッションではなく単純なサーバ状態で
> 「ログイン中の本人」を表現しています。実運用のクロスサイト環境では SameSite Cookie も
> 重要な防御層になります。

## モジュール7: 認可制御の欠落（IDOR / BOLA）

実在事例「**2019年 First American Financial の情報漏えい**」の再現です。書類URLが連番IDで、
ログインも所有者チェックも無かったため、ID を増減するだけで他人の不動産取引書類（社会保障番号や
銀行口座など）約8.85億件が誰でも閲覧できました。「本人のものかを確認し忘れた（認可制御の欠落 /
IDOR・BOLA）」典型例です。

架空SNS『つなぐ』では、ダイレクトメッセージ（DM）が連番IDで取得でき、取得時に「そのDMが本当に
リクエスト元ユーザーのものか」を確認していません（ログイン中ユーザーは学習用に `X-User` ヘッダで表現）。

### 攻撃を体験する

1. ラボ画面の左サイドバーで「認可制御の欠落」を選ぶ → DMビューアが開く。
2. `you` 本人のDMは id=1,4 だけのはずだが、id を `2` `3` に変えて取得すると、他人（samy / admin）の
   非公開DM（例: サーバの鍵、管理者パスワードの一時値）が読めてしまう。
3. 連番の総当たりボタンで、全ユーザーのDMを一気に収集できることを確認する。

### なぜ成立するのか（脆弱点）

`target/app.ts` の一覧 API `/api/messages` は `owner` で正しく絞っているのに、個別取得
`/api/messages/:id` が **`owner` とリクエスト元ユーザーの照合を忘れている**。

### 対策

個別取得でも `msg.owner === ログイン中ユーザー` を必ず確認し、他人のものなら `403/404` で
拒否します。「本人のリソースか」を**サーバ側で毎回検証**するのが根本対策です（`app.ts` のコメント
参照）。推測しにくいID（UUID 等）は補助にはなりますが、認可チェックの代わりにはなりません。

---

これで IPA「安全なウェブサイトの作り方」の主要な脆弱性（クリックジャッキング / XSS /
SQLインジェクション / OSコマンドインジェクション / パストラバーサル / CSRF / 認可制御の欠落）が
一通り揃いました。各モジュールは実在事例を踏まえた架空シナリオで「攻撃の成立」と「対策」を
対で学べます。
